# План реализации MVP: фреймворк прототипирования merge-2

Sep 28, 2026

План описывает, как построить MVP по ТЗ [merge_framework.md](merge_framework.md). Реализацию ведёт ИИ-агент, этапы выполняются строго последовательно: следующий этап начинается только после того, как у текущего выполнены все пункты «Готово, когда».

## 1. Решения, дополняющие ТЗ

Эти решения приняты после разбора ТЗ и имеют приоритет над ним там, где они расходятся.

| # | Тема | Решение |
| --- | --- | --- |
| 1 | Кулдаун генератора | У каждого уровня генератора есть `cooldown`: `charges` (сколько предметов выдаётся до кулдауна) и `seconds` (длительность кулдауна). Во время кулдауна тап не выполняется, интерфейс показывает оставшееся время. Новый генератор после слияния стартует с полным запасом зарядов. |
| 2 | Количество предметов для слияния | Сливаются всегда ровно два предмета. Поле `mergeCount` из схемы убирается; достижимость считается для слияния 2 → 1. |
| 3 | Время | Энергия, кулдауны, пузыри и пополнение слотов заказов идут по реальному времени, в том числе пока приложение закрыто (офлайн-прогресс применяется при запуске одним `tick`). Добавляется чит `skipTime` — «добавить N минут». |
| 4 | Сдача заказа | Кнопка «Сдать» на слоте активна, когда все требуемые предметы есть на доске (и в хранилище, если `allowFromStorage: true`). Списываются любые подходящие экземпляры; предметы в пузырях и замках не учитываются. |
| 5 | UI-стек | React для редактора и HUD, PixiJS для доски. |
| 6 | Поля схемы | В схему включаются `art.items`, `art.targetSizePx`, `art.promptTemplate`, `orders.refillDelaySec`, `orders.fallbackTemplate`; формат блока `cheats` задаётся явно (ниже). |
| 7 | Размер ассета | `art.targetSizePx` = 256 по умолчанию. |
| 8 | Пресеты | Пустой шаблон и один демо-пресет, который использует все блоки и все флаги конфига. |

### Изменения схемы относительно ТЗ

```jsonc
"generators": [
  { "id": "sawmill", "name": "Лесопилка",
    "levels": [
      { "energyCost": 1,
        "cooldown": { "charges": 10, "seconds": 300 },   // новое
        "produces": [ { "chain": "wood", "level": 1, "weight": 80 } ] }
    ] }
],
"cheats": {
  "addHard":      { "enabled": true, "amount": 100 },
  "refillEnergy": { "enabled": true },
  "skipLevel":    { "enabled": true },
  "skipTime":     { "enabled": true, "minutes": [10, 60, 240] }  // новое: кнопка на каждое значение
}
```

- `cooldown` необязателен; без него генератор работает без ограничений.
- `mergeCount` отсутствует; его наличие в конфиге — ошибка «неизвестное поле».
- Новые события журнала: `generator_cooldown_started`, `generator_cooldown_ended`, `time_skipped` (помечается как чит).
- Новые проверки валидатора: `cooldown.charges` < 1 или `cooldown.seconds` ≤ 0 — ошибка; пустой список `skipTime.minutes` при `enabled: true` — ошибка.

## 2. Архитектура и структура репозитория

Один Vite-проект на TypeScript (strict). Ядро не импортирует ничего из `render`, `ui`, `editor`, `platform`; это правило проверяется линтером (`eslint-plugin-boundaries` или `no-restricted-imports`).

```
src/
  config/      Zod-схема, значения по умолчанию, экспорт JSON Schema, пресеты
  expr/        мини-язык формул: лексер, парсер, вычислитель (без eval)
  core/        состояние, команды, правила, seeded RNG, время, журнал событий
    reach/     анализ достижимости (используется ядром и валидатором)
  validator/   логические проверки поверх Zod, сообщения с путём и подсказкой
  telemetry/   счётчики из журнала, сессии, экспорт JSON и CSV
  render/      PixiJS: доска, drag и tap, плейсхолдеры, загрузка ассетов
  ui/          React HUD: энергия, заказы, хранилище, валюта, действия, читы, метрики
  editor/      React: форма из JSON Schema, JSON-редактор, сетка раскладки
  platform/    хранение (IndexedDB в браузере, Capacitor Filesystem на Android), «Поделиться», файлы
  i18n/ru.ts   все строки интерфейса
presets/       empty.json, demo.json
scripts/art/   bake.ts, prompts.ts, import.ts, postprocess.ts
tests/         фикстуры конфигов, журналы команд для replay-тестов
android/       проект Capacitor (генерируется)
```

**Контракт ядра.** `apply(state, command) → { state, events[] }` — чистая функция. Команды: `tapGenerator`, `move`, `merge`, `deliverOrder`, `popBubble`, `pickUp`, `returnFromStorage`, `delete`, `sell`, `cheat`, `tick(dtMs)`. Время попадает в ядро только через `tick`; `Date.now()` вызывается только снаружи ядра. Это даёт детерминизм и готовность к ботам.

**RNG.** Собственная реализация (например, xoshiro128**) с отдельным потоком на подсистему: `generators`, `orders`, `bubbles`, `rewards`. Потоки выводятся из `meta.seed`, поэтому изменение одной подсистемы не сдвигает случайность в других.

**Стек библиотек.** Vite, TypeScript, React, PixiJS, Zod, `zod-to-json-schema`, `@rjsf/core` (форма), CodeMirror 6 (JSON), Vitest, Playwright (смоук в браузере), Capacitor, `sharp` и `@google/genai` (скрипты арта).

## 3. Правила работы ИИ-агента

- В начале этапа 0 создаётся `CLAUDE.md` с командами проекта, структурой модулей и правилами ниже; агент обновляет его при изменениях.
- Каждая задача: код, тесты к ней, `npm run check` (lint + prettier + typecheck + test) зелёный. Агент не делает коммиты и push — их делает пользователь.
- Этап закрывается, когда выполнены все пункты «Готово, когда»; итог этапа фиксируется в разделе 6 этого документа (статус и заметки). Следующий этап начинается только после явного подтверждения пользователя.
- Спорные места ТЗ не додумываются молча: агент записывает вопрос в раздел 7 и выбирает вариант по умолчанию, помечая его в коде `// DECISION:`.
- Строки интерфейса только через `i18n/ru.ts`.
- Внешние API (модель Gemini для картинок, версии Capacitor и RJSF) сверяются с актуальной документацией перед использованием.

## 4. Этапы

### Этап 0. Каркас

- Vite + React + TS strict, алиасы путей, ESLint, Prettier, правило границ модулей.
- Vitest, Playwright, скрипт `npm run check`.
- GitHub Actions: `check` и `build:web` на каждый push.
- Пустые модули по структуре раздела 2, `i18n/ru.ts`, `CLAUDE.md`.

**Готово, когда:** `npm run dev` открывает пустую страницу, `npm run check` и CI зелёные.

### Этап 1. Схема, формулы, ядро доски, плейсхолдерный рендер

- Zod-схема всех блоков конфига с `.strict()`, значения по умолчанию, типы, экспорт JSON Schema (`npm run schema`).
- Мини-язык формул: переменные `level`, `itemValue`, `totalValue`, `boardLevel`, `ordersDone`; функции `ceil`, `floor`, `round`, `min`, `max`; операторы `+ - * / ^` и скобки. Ошибки разбора с позицией.
- RNG, выбор по весам, диапазоны `[min, max]`.
- Ядро: разбор ASCII-раскладки, перемещение, слияние двух предметов и двух генераторов, тап по генератору (энергия, выбор по весам, ближайшая свободная клетка, причина отказа), заряды и кулдаун генератора, энергия с регенерацией и `allowOverMax`.
- Журнал событий с первого дня: `energy_spent`, `item_spawned`, `merge`, `generator_cooldown_*`.
- PixiJS-доска 7×9: drag мышью и тачем, tap, плейсхолдеры (цвет по цепочке, название, уровень), индикатор кулдауна; минимальный HUD энергии.
- Пробная сборка Android (Capacitor, debug APK), чтобы заранее проверить тач и производительность; полная сборка остаётся в этапе 5.

**Готово, когда:**
- юнит-тесты покрывают формулы, RNG, слияние, генерацию, кулдаун, энергию;
- replay-тест: конфиг + seed + журнал команд дают одинаковый хеш состояния при повторных прогонах;
- на доске с плейсхолдерами можно генерировать и сливать предметы в браузере;
- debug APK устанавливается и запускается, drag работает пальцем.

### Этап 2. Игровые системы

- Замки: состояния sealed → unlockable → открыт; слияние с замком оставляет результат в клетке; `lock_opened`.
- Хранилище без лимита: стеки по (цепочка, уровень), `returnToBoard`, неактивная кнопка с подсказкой при полной доске.
- `itemActions`: сопоставление `цепочка.уровень`, `цепочка.*`, `generator.id`, `*`; первое совпадение; действия «забрать», «удалить», «продать».
- Достижимость (`core/reach`): источники по `countSources`, слияние 2 → 1, `maxMergeDepth`, `orderLevelCap`, предметы на доске и в хранилище, `onNoValidTemplate`.
- Заказы: слоты, `refillDelaySec`, фильтр по `boardLevels`, фильтр достижимости, выбор по весам, развёртка требований с `maxRequirements`, `totalValue`, награды `energy`, `hard`, `item` (при нехватке места — в хранилище); кнопка «Сдать» по решению 4.
- Пузыри: появление от генератора (`chance`) и по таймеру (`everySec`, `maxOnBoard`, `content`), время жизни (число, диапазон, `null`), `vanish`, лопание по `popCost`, блокировка с подсказкой при нехватке валюты, пропуск появления при полной доске.
- Уровни доски: `ordersRequired`, `unlocks`, награды, бесконечные заказы после последнего уровня.
- Читы: `addHard`, `refillEnergy`, `skipLevel`, `skipTime`; все пишутся в журнал с пометкой `cheat: true`.
- Офлайн-прогресс: при запуске ядро получает `tick` на прошедшее время.
- HUD: энергия (значение, максимум, время до следующей единицы), заказы, прогресс уровня, хранилище, валюта, меню действий над предметом, панель читов.
- Локальное сохранение партии и последнего конфига через `platform`.

**Готово, когда:**
- тесты на каждое правило, включая граничные случаи (полная доска, нет энергии, кулдаун, энергия выше максимума, пузырь истёк во время офлайна);
- property-тест достижимости: на случайных конфигах ни один сгенерированный заказ не требует недостижимого предмета;
- в демо-сценарии проходится минимум два уровня доски с открытием замков.

### Этап 3. Валидатор, телеметрия, редактор, пресеты

- Валидатор: все проверки из раздела 12 ТЗ и из раздела 1 этого плана; каждое сообщение содержит путь, текст и подсказку; уровни «ошибка» и «предупреждение».
- Телеметрия: счётчики по `match` и `sources`, энергия всего и по генераторам, заказы, пузыри, потраченная хард-валюта, длительность сессии; разбивка на сессии, сохранение между запусками; фильтр читов.
- Панель метрик в прототипе; экспорт JSON (сводка, счётчики, полный журнал) и CSV (счётчики, энергия по генераторам).
- Редактор:
  - форма из JSON Schema (RJSF с кастомными виджетами для формул и ссылок на `id`);
  - JSON-режим на CodeMirror 6; оба режима работают с одной моделью; при невалидном JSON форма блокируется, ошибка подсвечивается;
  - редактор сетки раскладки с палитрой из легенды и отображением замков;
  - ошибки и предупреждения рядом с полями;
  - загрузка из файла, скачивание, выбор пресета или пустого шаблона;
  - «Запустить прототип»: ошибки блокируют, предупреждения нет.
- Пресеты: `empty.json` и `demo.json`, где задействованы все блоки и флаги (кулдауны, замки, хранилище с возвратом, все типы наград, оба источника пузырей, `orderLevelCap`, `fallbackTemplate`, все читы, несколько счётчиков).

**Готово, когда:**
- на каждую проверку валидатора есть тест с неправильным конфигом;
- `demo.json` проходит валидацию без ошибок и запускается;
- Playwright-смоук: открыть редактор → поменять поле в форме → увидеть изменение в JSON → запустить → сделать ход → экспортировать метрики;
- значения метрик в экспорте совпадают с пересчётом по журналу событий в тесте.

### Этап 4. Арт-пайплайн

- Перед началом: сверить актуальную модель Gemini для генерации изображений, её лимиты и SDK.
- `postprocess.ts`: вырезание фона по `chromaKey` (зелёный; маджента для зелёных предметов), обрезка по границам, приведение к `targetSizePx`.
- `art:prompts`: папка `art-pack/` с `prompts.md`, `prompts.csv`, `prompts.json`, таблицей имён файлов и чек-листом требований.
- `art:import <папка>`: проверка имён и размеров, постобработка, копирование в ассеты, отчёт о недостающих и отклонённых файлах.
- `art:bake`: генерация по цепочкам, первый уровень как референс для остальных, кэш по хешу (название, стиль, версия модели), ключ только из переменной окружения.
- Приоритет в рендере: `art.overrides` → сгенерированный ассет → плейсхолдер; учёт `art.mode` и `art.items`.
- Редактор: переключатель режима, «Копировать промпт», слот перетаскивания картинки, перегенерация одного предмета через локальный dev-эндпоинт Vite (ключ остаётся на стороне Node).

**Готово, когда:**
- тесты постобработки на эталонных картинках;
- ручной режим проверен на наборе картинок демо-пресета; авто-режим проверен при наличии ключа;
- проверка сборки: в `dist/` нет ключа и скриптов арта;
- прототип без ассетов по-прежнему работает на плейсхолдерах.

### Этап 5. Android и приёмка

- `build:android`: копирование выбранного конфига и ассетов, `build:web`, `cap sync`, Gradle, APK в `dist/android/`.
- Workflow GitHub Actions для сборки APK без локального JDK и SDK.
- На устройстве: зашитый конфиг, локальное сохранение, экспорт метрик через системное «Поделиться».
- Проверка 30 FPS на доске 7×9 на устройстве с Android 11.
- Прогон всех критериев приёмки (раздел 5).

**Готово, когда:** все критерии раздела 5 отмечены, APK собирается локально и в CI.

## 5. Критерии приёмки MVP

Критерии ТЗ с учётом решений раздела 1.

Прогон на этапе 5 (2026-10-01). В скобках — чем подтверждено.

- [x] Конфиг со всеми блоками загружается, проходит валидацию и запускает играбельный прототип (`demo.json`). *(validator.test: демо без замечаний; e2e «редактор → … → запуск»; бот проходит оба уровня демо.)*
- [x] Форма и JSON-режим редактора синхронны; конфиг можно загрузить из файла и скачать. *(e2e editor.spec: правка формы видна в JSON, загрузка файла, блокировка при ошибке JSON; скачивание — кнопка «Скачать».)*
- [x] Слияние, генераторы (в том числе слияние генераторов и кулдаун), замки, хранилище и действия над предметами работают по правилам. *(unit: engine, locks-storage; e2e: слияние перетаскиванием, хранилище туда-обратно, замки после пропуска уровня; Android 11 — слияние пальцем.)*
- [x] Заказы генерируются по шаблонам, сдаются кнопкой, награды выдаются, недостижимых заказов нет. *(unit: orders; property-тест достижимости на 60 случайных конфигах; e2e orders.spec: сдача кнопкой, награды заказа и уровня.)*
- [x] Пузыри появляются, исчезают по времени и лопаются за хард-валюту; читы добавляют валюту, энергию, проходят уровень и сдвигают время. *(unit: bubbles-cheats; e2e: читы.)*
- [x] Офлайн-прогресс: после перезапуска энергия, кулдауны и пузыри соответствуют прошедшему времени. *(unit: длинный tick = много коротких; e2e: перезагрузка страницы; Android 11: приложение закрыто ~70 с — энергия восстановилась, появился пузырь по таймеру.)*
- [x] Метрики (энергия и заданные счётчики) считаются верно и экспортируются в JSON и CSV; чит-действия отфильтровываются. *(telemetry.test: сверка с независимым пересчётом на 3000 ходах; e2e: экспорт JSON и CSV с проверкой файлов; Android 11: экспорт через «Поделиться», файл проверен.)*
- [ ] Авто и ручной режимы арта дают ассеты в одном стиле; без арта работают плейсхолдеры. *(Ручной режим и плейсхолдеры — проверены, в т. ч. в APK. **Авто-режим не проверен вживую:** у ключа Gemini нет квоты на модели картинок — см. раздел 7.)*
- [x] Одинаковые конфиг, seed и журнал команд воспроизводят одну и ту же партию. *(replay.test: хеш состояния на 500 командах, склейка тиков.)*
- [ ] Прототип запускается в Chrome на Windows и macOS; `npm run build:android` даёт APK, который запускается на устройстве. *(Windows: Chromium/Chrome — e2e. APK: собирается локально, запущен на эмуляторах Android 11 (WebView 83) и Android 17. **Не проверено:** macOS, физическое устройство, сборка APK в GitHub Actions — нужен push.)*

Производительность: доска 7×9, ~45 предметов, пузыри и таймеры, непрерывные тапы и перетаскивания — 60 FPS (минимум за 5 с — 60) по встроенному счётчику; `dumpsys gfxinfo`: 99-й перцентиль кадра 20 мс (≥ 50 FPS). Эмулятор Android 11 на ПК — на слабом телефоне цифры будут ниже; счётчик FPS включается в «Читах».

### Решения, принятые при реализации

Места, которые ТЗ не описывает; в коде помечены `// DECISION:`. Пользователь может пересмотреть любое.

| Этап | Решение |
| --- | --- |
| 1 | Перенос предмета на другой (не сливаемый) предмет меняет их местами. Слияние выполняется той же командой `move`, отдельной команды `merge` нет. |
| 1 | Новый предмет из генератора кладётся в ближайшую свободную клетку по манхэттенскому расстоянию; при равенстве — клетка выше, затем левее. |
| 1 | Координаты клеток замков — `[x, y]` (столбец, строка), `(0, 0)` — левый верхний угол. |
| 1 | Ключи арта: `цепочка:уровень` для предметов, `generator.id:уровень` для генераторов. |
| 1 | У уровня генератора есть необязательное поле `name` (название для интерфейса и арта), по умолчанию — имя генератора. |
| 1 | Веб-билд собирается под Chromium 83: это стоковый WebView Android 11 без обновлений из Google Play. CSS без `dvh`, `color-mix` и flex `gap` или с фоллбэками. |
| 2 | Тап по предмету выделяет его и показывает доступные действия; тап по генератору генерирует и тоже выделяет его (так доступно «Забрать» для генератора). Тап по пузырю показывает кнопку «Лопнуть». |
| 2 | Предмет в пузыре нельзя перемещать (не только сливать и сдавать) — только лопнуть. Пузырь по таймеру появляется в случайной свободной клетке. |
| 2 | Генератор на кулдауне забрать в хранилище нельзя; генератор из хранилища возвращается с полными зарядами. |
| 2 | Если требований в шаблоне больше `maxRequirements`, берётся случайное подмножество; требования к одному предмету складываются. |
| 2 | При сдаче заказа сначала списываются предметы с доски (в порядке чтения), затем из хранилища (если `allowFromStorage`). |
| 2 | Предмет-награда кладётся в первую свободную клетку (порядок чтения), при полной доске — в хранилище, даже если оно выключено (чтобы награда не пропала). |
| 2 | Результаты формул наград, стоимости пузыря и продажи округляются до целого, не меньше 0. В наградах уровня `totalValue` = 0. |
| 2 | `boardLevel` — поле `id` текущего уровня. После последнего уровня игра остаётся на нём, заказы генерируются по его правилам. |
| 2 | Достижимость: источник `generator` — генераторы на доске (и в хранилище, если разрешён возврат) на их текущем уровне, слияние генераторов не учитывается; `lockedCellsAfterUnlock` — содержимое замков открываемых групп + 1 уровень; `bubble` — содержимое пузырей по таймеру; `reward` — предметы-награды шаблонов и текущего уровня. Предметы на доске и в хранилище доступны ровно своего уровня. |
| 2 | `fallbackTemplate` берётся без учёта `boardLevels`, но с проверкой достижимости; если и он не проходит — слот ждёт смены условий. |
| 2 | Партия сохраняется в localStorage (в Android — хранилище WebView приложения) с хешем конфига: при другом конфиге начинается новая партия. |
| 3 | Редактор открывает последний черновик (сохраняется как текст, даже невалидный) или демо-пресет. Форма разбита на вкладки по блокам; на широком экране форма и JSON видны рядом, на узком — переключателем. |
| 3 | Форма не дописывает в конфиг значения по умолчанию — они показаны в описании поля. Предупреждения валидатора в форме видны рядом с полем со значком ⚠. |
| 3 | Валидатор: диапазон уровней в требованиях — ошибка, только если он целиком выше максимума цепочки; диапазон счётчика телеметрии может быть шире цепочки (`[1, 99]` = «любой уровень»). |
| 3 | Предупреждения о достижимости по уровням и об источнике для замка считаются по стартовой доске: генераторы и предметы раскладки, замки групп, открытых к этому уровню. |
| 3 | Сессия телеметрии — один запуск прототипа (или «Начать заново»); длительность — реальное время с открытым прототипом. Сессии хранятся в IndexedDB; экспорт включает все сессии текущего конфига. «Потрачено хард-валюты» — на лопание пузырей (других трат в MVP нет). |
| 3 | CSV: разделитель «;» и BOM — файл сразу открывается по столбцам в Excel с русской локалью. |
| 4 | Gemini: эндпоинт `interactions`, модель по умолчанию `gemini-3.1-flash-image` (меняется переменной `ART_MODEL` или `--model`). API отдаёт только JPEG, поэтому прозрачность всегда получается вырезанием фона. |
| 4 | Готовые ассеты лежат в `public/art/<id>.png` + `public/art/index.json` (попадают в веб-билд и APK). `id` — хеш промпта и размера: другое название, стиль или шаблон — новый ассет, старый остаётся в кэше. В индексе записаны источник (`auto`/`manual`) и модель; другая модель — повод перегенерировать в авто-режиме. |
| 4 | Пути в `art.overrides` — относительно папки `public/`. Свои картинки используются как есть, без постобработки. |
| 4 | Цвет фона для зелёных предметов (маджента) задаётся вручную в `art.items[ключ].chromaKey` (в редакторе — выпадающий список); автоматически не определяется. |
| 4 | Все ассеты вписываются в одинаковый квадрат — уровень на доске отличает значок с номером, а не размер картинки. |
| 4 | Референс для уровней 2+ — готовый ассет уровня 1 той же цепочки (сгенерированный, импортированный или свой), подложенный на цвет фона. «Утверждение» уровня 1 — это просто наличие его ассета. |
| 4 | Генерация и импорт из редактора работают только в `npm run dev` (эндпоинты `/__art/*` локального сервера): ключ остаётся в Node. `art:bake` не генерирует предметы в ручном режиме, даже с `--only`. |
| 4 | Для проверки ручного режима в `public/art` импортированы простые нарисованные скриптом картинки демо (`scripts/art/fixtures/make-demo-art.ts`). Их можно удалить (`public/art`) или заменить своими — без арта работают плейсхолдеры. |
| 5 | Конфиг для APK выбирается аргументом `npm run build:android -- путь/к/конфигу.json` (по умолчанию демо); с ошибками валидации APK не собирается. В APK попадают только ассеты арта этого конфига. |
| 5 | Счётчик FPS — галочка «Показывать FPS» в панели читов (не сохраняется между запусками). |
| 3 | В приложении (Android) редактора нет: прототип запускается сразу с конфигом, зашитым при сборке (этап 5); метрики выгружаются через «Поделиться». |
