## 4. Решения

Ответы от 2026-10-04. Имеют приоритет над текстом спеки там, где они расходятся.

| # | Вопрос | Решение | Что это значит для реализации |
| --- | --- | --- | --- |
| Р1 | Генерация «за цикл» | `produced_objects` + `count_per_cycle` — точное количество объектов каждого типа за цикл генератора (до кулдауна). Один тап — один объект. | Режим «мешка»: в начале цикла генератор набирает мешок (например, 3 × A_01, 2 × A_02, 1 × B_01), каждый тап достаёт из него один случайный объект. Мешок пуст — кулдаун `reload_time`. Слияние генератора даёт новый полный мешок. Режим весов (как сейчас) остаётся для старых конфигов. |
| Р2 | Уровень игрока | Растёт от выполненных заказов. | Используем существующие уровни (`levels[].ordersRequired`), называем их в интерфейсе «уровень игрока». `required_level` клеток, распределение заказов и минимальный уровень пузырей считаются по нему. Чит «пройти уровень» остаётся. |
| Р3 | Какие объекты — специи | По списку вкладки Spice Chain Order. | Флаг «собираемый» у объекта (`collectable`); импорт выставляет его объектам из Spice Chain Order. Только собираемые объекты попадают в заказы и собираются двойным тапом на склад специй. |
| Р4 | `base_cost` | Стоимость лопания пузыря. | Поле `baseCost` у уровня цепочки; `bubbles.popCost` по умолчанию = `baseCost` (переменная `baseCost` в формуле). |
| Р5 | Заказы | 4 категории: easy, medium, hard, super hard. Одновременно 6 заказов. | Слотов всегда 6; Orders Allocation задаёт, сколько слотов какой категории на уровне (см. Р5.1). |
| Р6 | Импорт | Нужен импорт из таблицы в конфиг. | `npm run import:sheet <файл.xlsx>` и загрузка `.xlsx` в редакторе. ### Оставшиеся вопросы

Не блокируют старт; до ответа берётся вариант «по умолчанию».

- **Р1.1. `cooldown_cycle` при режиме мешка.** У генератора 1-го уровня `cooldown_cycle = 15`, а в мешке 1 объект. Если цикл = мешок, что тогда означает 15? *По умолчанию:* `cooldown_cycle` — число тапов до кулдауна; мешок, опустев раньше, набирается заново; генератор 1-го уровня выдаёт 15 × A_01, затем кулдаун.
- **Р5.1. Распределение заказов не всегда даёт 6.** В Orders Allocation сумма по уровням: 5 → 5, 7 → 6, 10 → 7, 15 → 7, 20 → 7, 30 → 7. *По умолчанию:* числа — пропорции; 6 слотов делятся по ним с округлением, лишние или недостающие слоты — в самую частую категорию. Альтернатива — слотов столько, сколько в строке таблицы.
- **Р5.2. Награды заказов** (`Order Rewards`) заданы для типов `ordinary` и `hard`, а категорий четыре. *По умолчанию:* easy и medium берут награды `ordinary`, hard и super hard — `hard`.
- **В4. Наградные цепочки.** На каком уровне объект наградной цепочки (`object_E1`…, `object_K1`…) превращается в ресурс и сколько даёт? *По умолчанию:* объект максимального уровня цепочки собирается двойным тапом и даёт ресурс из новой колонки `collect_reward` (в таблице её нет — импорт сообщит).
- **В6. Бонусный заказ.** В Settings нет `bonus_order_queue_min/max`. *По умолчанию:* 3–5 заказов, импорт сообщит о значении по умолчанию.

## 5. План работ

Этапы выполняются по одному, после каждого — остановка до подтверждения (как в MVP). Каждый этап включает: схему конфига, проверки валидатора с подсказками, поля в редакторе, события и счётчики телеметрии, unit- и e2e-тесты; `npm run check` зелёный.

### Этап S1. Объекты и генераторы

- Свойства уровня цепочки: `deletable`, `collectable`, `baseCost`, `bubbleProbability` (последнее используется в S2).
- Сбор собираемого объекта двойным тапом на склад специй (без награды); остальные объекты двойным тапом не собираются.
- Генератор: режим мешка (Р1, Р1.1), `uses` — исчезновение после N тапов, пропуск кулдауна за хард: `skipCost` с уменьшением пропорционально остатку и бесплатным окном `freeSkipSec`.
- Значок «максимальный уровень» у простых объектов.
- Дополнительные ресурсы (кристаллы, билеты и т. п.) как счётчики; награды и метрики по ним.
- Награда-генератор за уровень (генератор кладётся на поле или в склад).

**Готово, когда:** на тестовом конфиге проходят сценарии «мешок выдаёт ровно заданные объекты и уходит в кулдаун», «пропуск кулдауна списывает хард по остатку времени, в бесплатном окне — бесплатно», «генератор исчезает после `uses`», «специя собирается двойным тапом, обычный объект — нет»; демо обновлён и проходит валидацию.

### Этап S2. Пузыри из слияния

- Источник пузыря `merge`: с вероятностью `bubbleProbability` результата слияния рядом появляется его копия в пузыре (ближайшая свободная клетка).
- Общий лимит `bubbles.maxOnBoard`, минимальный уровень игрока для появления, время жизни (уже есть).
- Перемещение пузыря (флаг `bubbles.movable`, для Spice — включён): в свободную клетку или обмен местами.
- Цена лопания по умолчанию — `baseCost` объекта (Р4).

**Готово, когда:** тесты на вероятность (на фиксированном seed), лимит, минимальный уровень и перемещение; старые источники пузырей работают как раньше.

### Этап S3. Поле

- Состояние клетки: закрыта по уровню игрока (`required_level`, первый приоритет) → после уровня закрыта («песок») / заблокирована / открыта.
- «Песок»: открывается слиянием в соседней по вертикали или горизонтали клетке; слияние в заблокированную клетку открывает её закрытых соседей; слияние в открытой клетке соседей не открывает.
- Заблокированная клетка — существующий замок, но без групп: открывается слиянием такого же объекта, когда клетка вышла из закрытия по уровню.
- Сообщения по тапу: «Достигните уровня N», «Расчистите объекты рядом», «Предмет заблокирован»; серые иконки.
- Генератор в закрытой по уровню клетке недоступен до уровня.

**Готово, когда:** тесты на все переходы состояний и правило соседей; поле 9×7 из таблицы (вручную собранный конфиг) отображается и играется; валидатор ловит объект максимального уровня в заблокированной клетке.

### Этап S4. Заказы по сложности

- Режим `orders.mode: "difficulty"` рядом с шаблонами: «цена» специи (`#merge_price`) → сложность заказа как сумма; категории easy / medium / hard / super hard по диапазонам Orders Difficulty.
- 6 слотов, категории слотов по Orders Allocation и уровню игрока (Р5.1); новый заказ появляется сразу.
- В заказе только собираемые объекты, 2–3 специи; заказ подбирается так, чтобы сумма попала в диапазон категории и специи были достижимы.
- Награды по весам Order Rewards (Р5.2): объект наградной цепочки выпадает на поле; объект наградной цепочки при сборе даёт ресурс (В4).

**Готово, когда:** property-тест — на случайных состояниях заказ каждой категории попадает в свой диапазон и содержит только достижимые специи; распределение категорий соответствует уровню; награды выпадают по весам (проверка частот на seed).

### Этап S5. Бонусный заказ

- Появляется после N выполненных заказов (N случайно в `bonus_order_queue_min…max`), только когда открыты все генераторы.
- Тир по весу → цена в диапазоне Bonus Order → специи; длительность случайно в `bonus_order_time_min…max`; по истечении исчезает.
- Награды по весам Bonus Order Reward (ресурсы и объекты).
- В интерфейсе — отдельная плашка с таймером сверху списка заказов.

**Готово, когда:** тесты на очередь, условие «все генераторы открыты», истечение (в том числе офлайн) и награды; события `bonus_order_created / completed / expired` и метрики по ним.

### Этап S6. Импорт таблицы

- `npm run import:sheet <файл.xlsx> [--out presets/spice.json]` и кнопка «Импорт из таблицы» в редакторе.
- Чтение вкладок Settings, Objects, Interactables, Chains, Spice Chain Order, Orders Allocation / Difficulty / Rewards, Bonus Order / Reward, Field, Bubbles; служебные вкладки `#…` пропускаются.
- Перевод id объектов в цепочки и уровни, координат поля из 1-базы, генерация легенды и раскладки.
- Отчёт: что импортировано, что взято по умолчанию (Р1.1, Р5.1, Р5.2, В4, В6), какие поля и строки не поддержаны и почему; результат сразу проходит валидатор.

**Готово, когда:** выгруженная из Google Таблиц «Core Merge Config» импортируется в конфиг без ошибок валидации, прототип по нему запускается в браузере и на Android, отчёт импорта перечисляет все значения по умолчанию.

### Вне плана

FTUE, иконка входа и `access_level`, админка, офферы при нехватке валюты, панель наград над заказами, энергия за специю в заказах кофейни, «справочник» цепочки (можно добавить позже как отдельную задачу).

### Решения, принятые при реализации S1

| Решение |
| --- |
| `uses` считается в тапах для режима весов и в циклах для режима мешка (для `generator_Converter` — 1 цикл = весь мешок). |
| Новый мешок набирается сразу, как только опустел предыдущий; после кулдауна восстанавливаются только циклы. Слияние, возврат со склада и награда дают генератор с полным мешком, циклами и `uses`. |
| Цена пропуска кулдауна = `ceil(skipCost × оставшееся / длительность)`; в последние `freeSkipSec` — 0. Пропуск — отдельное событие `generator_cooldown_skipped`; хард на пропуски входит в метрику «Потрачено хард-валюты». |
| Флаг `deletable` у объекта важнее правил `itemActions`; если флага нет — решает `itemActions`, как раньше. |
| Двойной тап собирает только предметы с `collect`; на остальных ничего не происходит, сообщение об отказе не показывается. В панели выбранного предмета есть та же кнопка «Собрать» / «Забрать». |
| Собранная специя попадает на склад даже при выключенном хранилище (валидатор предупреждает). |
| Генератор-награда ставится в первую свободную клетку; если места нет — ждёт в очереди и встаёт автоматически, когда клетка освободится (в HUD — «ждут места: N»). Предметы-награды по-прежнему уходят на склад при полной доске. |
| Слияние двух предметов последнего уровня в генератор (`mergesInto`) — событие `merge` с полем `intoGenerator`; в счётчики «слиянием» оно не засчитывается. |
| Значок ★ — у предмета последнего уровня, у которого нет `mergesInto` (его дальше нельзя слить). |

### Решения, принятые при реализации S3

| Решение |
| --- |
| «Песок» расчищает только слияние в заблокированную соседнюю клетку (спека: «мердж в открытой клетке не меняет состояние соседних закрытых клеток»). Клетка, которая в этот момент ещё закрыта по уровню, «песок» сохраняет: уровень снимает только своё условие. |
